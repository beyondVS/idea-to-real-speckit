## 0. 문제 정의 및 본질 분석 (Problem Definition & Root Cause) *(필수)*

<!--
  헌법 제1조(Problem Space First)에 따라, 해결책을 제시하기 전에 문제의 본질을 정의합니다.
-->

**문제의 본질**: 사용자는 자신의 아이디어나 문제 상황을 모호하게 인지하고 있으며, 이를 개발 가능한 수준의 구체적인 요구사항이나 문제 기술서로 변환하는 데 어려움을 겪습니다. 초기 단계에서 문제의 본질(Root Cause)이 명확히 규명되지 않으면, 잘못된 해결책을 설계하게 되어 자원이 낭비되는 근본적인 문제가 발생합니다.

**분석**: 
- 사용자는 증상(Symptom)과 원인(Cause)을 혼동하는 경향이 있음.
- 논리적 비약이나 숨겨진 전제를 스스로 인지하기 어려움.
- 체계적인 질문(5 Whys 등) 없이는 심층적인 문제 공간(Problem Space) 탐색이 불가능함.

## 사용자 시나리오 및 테스트 (User Scenarios & Testing) *(필수)*

### 사용자 스토리 1 - 문제 입력 및 진단 시작 (우선순위: P1)

사용자가 모호한 문제 상황(예: "우리 팀의 생산성이 너무 낮은 것 같아요")을 입력하면, AI 에이전트는 사용자의 답변에서 핵심 페르소나와 배경을 추출하고 공감 어린 태도로 첫 번째 심층 질문을 던집니다.

**우선순위 선정 이유**: 시스템의 진입점이자 진단 프로세스의 시작으로, 핵심 가치인 문제 탐색의 기초가 됩니다.

**독립적 테스트 (Independent Test)**: 모호한 문장을 입력했을 때 AI가 텍스트에서 메타데이터를 추출하고 첫 번째 "Why" 질문을 정상적으로 출력하는지 확인합니다.

**수락 시나리오 (Acceptance Scenarios)**:

1. **Given** 사용자가 메인 화면에서 모호한 문제를 입력할 때, **When** '분석 시작'을 누르면, **Then** 시스템은 대화 상태(GraphState)를 초기화하고 첫 번째 질문을 제시해야 한다.
2. **Given** 대화가 시작되면, **When** 시스템이 첫 번째 답변을 분석하면, **Then** 답변에 포함된 사용자 페르소나와 환경적 배경 정보가 메타데이터로 추출되어야 한다.

---

### 사용자 스토리 2 - 5 Whys 심층 문답 진행 (우선순위: P1)

사용자와 AI 에이전트는 최대 5회에 걸쳐 문답을 주고받습니다. AI는 이전 답변의 논리적 허점을 찌르거나 숨겨진 전제를 파악하여 인과관계를 깊게 파고드는 질문을 생성합니다.

**우선순위 선정 이유**: 문제의 근본 원인을 파악하기 위한 핵심 로직(Questioner Node)이 작동하는 구간입니다.

**독립적 테스트 (Independent Test)**: 3~5회의 문답 과정에서 질문의 깊이가 점진적으로 깊어지며, 인과관계가 논리적으로 연결되는지 확인합니다.

**수락 시나리오 (Acceptance Scenarios)**:

1. **Given** AI가 질문을 생성할 때, **When** 이전 답변에 논리적 비약이 있다면, **Then** 해당 비약을 확인하기 위한 질문을 우선적으로 생성해야 한다.
2. **Given** 질문 단계가 진행됨에 따라, **When** GraphState의 질문 단계(Step)가 1에서 5까지 순차적으로 증가해야 한다.

---

### 사용자 스토리 3 - 진단 종료 및 문제 기술서 생성 (우선순위: P1)

근본 원인이 파악되었거나 질문이 5단계에 도달하면 대화가 자동 종료됩니다. 시스템은 수집된 모든 정보를 구조화하여 Markdown 및 JSON 형식의 '문제 기술서'를 생성하여 사용자에게 제공합니다.

**우선순위 선정 이유**: 진단 결과물을 사용자에게 전달하는 최종 단계로, 후속 개발 단계의 입력값이 됩니다.

**독립적 테스트 (Independent Test)**: 대화 종료 후 생성된 파일에 표면적 문제, 인과관계 연쇄, 최종 근본 원인이 모두 포함되어 있는지 검증합니다.

**수락 시나리오 (Acceptance Scenarios)**:

1. **Given** 질문이 5단계에 도달하거나 근본 원인이 파악되면, **When** 엣지 로직(Edge Logic)이 작동하면, **Then** 대화가 즉시 종료되고 결과 생성 단계로 전이되어야 한다.
2. **Given** 결과물이 생성되면, **When** 파일 내용을 확인하면, **Then** '표면적 문제'부터 '최종 근본 원인'까지의 논리적 흐름이 포함되어야 한다.

---

### 사용자 스토리 4 - 롤백 및 대화 분기 관리 (우선순위: P1)

사용자는 대화 도중 이전 답변이 잘못되었음을 인지할 경우, 해당 시점으로 돌아가 답변을 수정하고 새로운 진단 경로를 탐색할 수 있습니다.

**우선순위 선정 이유**: 사용자의 실수나 생각의 변화를 유연하게 수용하여 진단의 정확도를 높이는 핵심 UX 요소입니다.

**독립적 테스트 (Independent Test)**: 특정 단계로 롤백 시 GraphState가 정상 복구되며, 수정된 입력에 따라 새로운 질문 분기가 생성되는지 확인합니다.

**수락 시나리오 (Acceptance Scenarios)**:

1. **Given** 3단계 질문이 진행 중일 때, **When** 사용자가 1단계 답변 수정을 요청하면, **Then** 시스템은 1단계 상태로 롤백하고 기존 대화 이력을 보존한 채 새 분기를 시작해야 한다.
2. **Given** 대화가 중단된 후 재접속할 때, **When** 대시보드에서 해당 세션을 선택하면, **Then** 마지막 중단 시점의 분기에서 즉시 대화가 재개되어야 한다.

---

### 예외 케이스 (Edge Cases)

- **무의미한 입력 처리**: 사용자가 "asdf", "ㅋㅋㅋ" 등 분석 불가능한 입력을 할 경우, 시스템은 분석에 실패했음을 알리고 문제의 증상을 구체적으로 다시 입력해달라는 안내 메시지를 출력해야 함.
- **주제 이탈 대응**: 사용자가 문제 진단과 전혀 관련 없는 질문이나 일상 대화를 시도할 경우, 시스템은 현재 진단 프로세스 중임을 환기시키고 원래 주제로 돌아올 수 있도록 유도해야 함.

## 요구사항 (Requirements) *(필수)*

### 기능적 요구사항 (Functional Requirements)

- **FR-001**: **Analyzer Node**: 사용자의 텍스트 입력에서 논리적 비약(Logical Leap)과 숨겨진 전제(Hidden Assumptions)를 식별해야 함.
- **FR-002**: **Questioner Node**: 분석된 결과와 대화 이력을 바탕으로 인과관계를 파고드는 5 Whys 질문을 생성해야 함. 사용자가 질문을 이해하지 못하겠다는 의사를 표시할 경우(예: "이해가 안 돼요", "무슨 뜻이죠?"), 더 쉬운 용어와 구체적인 맥락을 사용하여 질문을 자동으로 재구성하여 다시 제시해야 함.
- **FR-003**: **State Management**: LangGraph를 사용하여 대화 이력, 질문 단계(1~5), 메타데이터를 포함하는 GraphState의 무결성을 유지해야 함. 특히 사용자가 이전 단계로 돌아가 답변을 수정할 수 있도록 상태 롤백(Rollback) 기능을 지원해야 하며, 수정된 답변을 바탕으로 새로운 대화 분기를 생성하여 관리할 수 있어야 함. 이때 UI는 트리 구조나 드롭다운 형태의 '분기 탐색기'를 제공하여 사용자가 흐름을 명시적으로 전환할 수 있어야 함. PostgreSQL을 통해 모든 상태를 실시간으로 영구 저장하여 대화 중단 시(네트워크 단절, 새로고침 등) 대시보드의 세션 리스트를 통해 마지막 스냅샷으로부터 즉시 자동 재개가 가능해야 함.
- **FR-004**: **Edge Logic**: Analyzer Node에서 **`is_final_diagnosis: true`** 플래그가 반환되거나(인과관계의 논리적 수렴도가 에이전트 설정 임계치 0.8 이상인 경우), 질문이 5단계에 도달하면 사용자에게 진단 종료 여부를 묻고, 명시적인 동의를 얻은 후 대화를 종료하고 결과 생성 단계로 전이해야 함. (Clarifications 정렬)
- **FR-005**: **Result Generation**: 대화 종료 시 모든 상세 데이터를 포함하는 JSON(Full Spec)과 가독성을 고려한 Markdown(요약 보고서)을 동시에 생성해야 함. 특히 Markdown 보고서는 텍스트와 화살표를 이용한 '순차적 타임라인' 형식으로 인과관계 연쇄를 시각화하여 제공해야 하며, 사용자는 이 Markdown 보고서만 별도의 파일(.md)로 다운로드할 수 있어야 함. 각 결과물은 용도(MD: 가독성/공유, JSON: 시스템 연동)에 맞게 데이터베이스 필드를 분리하여 저장해야 하며, 세션 ID 및 생성 시간을 포함한 고유 ID를 가진 레코드로 이력을 보존해야 함. 저장된 데이터는 사용자가 명시적으로 삭제하기 전까지 영구적으로 보관되어야 함. JSON 데이터는 반드시 다음 필드를 포함해야 함: `initial_input` (최초 입력), `causal_chain` (인과관계 리스트), `identified_assumptions` (전제 목록), `final_root_cause` (최종 근본 원인), `metadata` (사용자 페르소나 및 배경).
- **FR-006**: **다국어 유연성**: 시스템은 한국어 입력을 우선적으로 처리하되, 타 언어 입력 시에도 LLM의 판단에 따라 유연하게 분석을 수행하고 문제 기술서를 생성해야 함. (단, 기본 인터페이스 및 공식 보고서는 한국어 품질을 최우선으로 함)
- **FR-007**: **Satisfaction Survey**: 진단 종료 후 사용자에게 결과에 대한 만족도 점수(1~5점)를 입력받아 저장해야 함. (성공 기준 SC-003 연동)

### 비기능적 요구사항 (Non-Functional Requirements)

- **NFR-001**: **신뢰성**: LLM API 호출 실패 시 지수 백오프 재시도 전략을 적용해야 함. Ollama 서버 미응답 또는 모델 부재 등 최종 실패 시 사용자에게 명확한 기술적 오류 상태를 알리고, 제한된 진단 결과를 보존하는 Fallback 전략을 포함해야 함. (헌법 V조 준수)
- **NFR-002**: **유지보수성**: 모든 내부 클래스 및 노드 로직에 한국어 Google Style Docstring을 작성해야 함.
- **NFR-003**: **성능**: 각 질문 생성 단계의 응답 시간은 P95 기준 5초 이내를 유지해야 함. 서버 부하 방지를 위해 Django 레벨에서 작업 큐(Task Queue)를 사용하여 요청을 순차적으로 처리하며, 대기 중인 사용자에게는 "분석 대기 중" 상태를 실시간으로 피드백해야 함. (수치 구체화)
- **NFR-004**: **보안**: 사용자의 입력 데이터에 포함된 민감 정보(개인 식별 정보(PII), 인증 토큰, 비밀번호 등)가 로그에 노출되지 않도록 필터링해야 하며, 데이터베이스 저장 전 자동 탐지 및 마스킹(Masking) 처리를 수행하여 보호해야 함.

### 주요 엔티티 (Key Entities)

- **InquirySession (DB Entity)**: Django 모델로 구현되며, Django Auth의 `User`와 외래 키(FK)로 연결되어 세션 소유권을 관리함. 본인 외 타 사용자의 접근은 기본적으로 차단되며, 대화의 메타데이터와 `GraphState`의 스냅샷을 PostgreSQL에 영구 저장하는 주체.
- **GraphState (Runtime State)**: LangGraph 내에서 전송되는 실시간 데이터 구조. `InquirySession`과 1:1로 매핑되어 복구 및 추적에 사용됨.
- **ProblemSpecification**: 최종 결과물인 문제 기술서 엔티티 (표면적 문제, 인과 연쇄, 전제, 근본 원인 포함).
- **Metadata**: 사용자의 페르소나, 배경 지식, 전문성 수준 등을 담는 정보.

## 성공 기준 (Success Criteria) *(필수)*

### 측정 가능한 결과 (Measurable Outcomes)

- **SC-001**: 모든 대화는 예외 없이 5단계 이내에 논리적으로 완결되어야 함.
- **SC-002**: 생성된 문제 기술서의 '인과관계 연쇄'가 최소 3단계 이상의 논리적 연결을 포함해야 함.
- **SC-003**: 사용자 만족도 조사에서 "생성된 질문이 문제의 핵심을 찌르는가?"라는 항목에 80% 이상의 긍정 응답률 확보.
- **SC-004**: 기술서의 JSON 데이터가 사전에 정의된 Schema 유효성 검사를 100% 통과해야 함.

## 가정 사항 (Assumptions)

- 사용자는 최소 1문장 이상의 구체적인 문제 증상을 입력한다.
- 시스템은 헌법에 따라 Python 3.13 및 Django 5.2 환경에서 구동되는 에이전트 아키텍처를 따른다.
- 대화의 흐름 제어는 LangChain 및 LangGraph를 통해 상태 기반으로 관리되며, 특정 LLM에 종속되지 않도록 추상화된 인터페이스를 통해 설계된다.
- 결과물 생성 시 지정된 데이터베이스(PostgreSQL)에 대한 쓰기 권한이 보장된다.
- 시스템은 사용자별 활성 및 누적 세션 수에 별도의 제한을 두지 않으며, 데이터 저장소는 이를 수용할 수 있는 충분한 확장성을 가진다고 가정한다.
- 단일 세션 내의 메시지 교환 횟수에도 별도의 제한을 두지 않으며, 상태 관리 로직(LangGraph)은 긴 대화 이력을 효율적으로 처리할 수 있도록 설계된다.
